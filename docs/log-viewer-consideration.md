# Global troubleshooting logs

Accepted on 2026-10-18 after comparing a contextual bottom panel with a single Logs page. Fairway's screens mainly control services and settings; students do their work in an editor, browser, or terminal. Logs are a destination for investigating a problem. This replaces the earlier site/global viewer proposal.

## Desktop experience

- **Logs** appears in the sidebar's core group, directly below Terminal. It is one global page, without per-screen viewers or automatic context changes. Service log buttons are shortcuts to this viewer with their source preselected and search cleared; separate dialogs are removed; Settings retains Open logs folder for inspecting original files.
- **Problems only** is on initially. It includes recognized errors/warnings, HTTP 4xx/5xx responses, and unclassified output. Turning it off includes routine service output and successful requests. Unfamiliar output is never silently excluded as routine activity.
- **Site** defaults to All sites. Registered site addresses and hosts recorded in recent requests are available. Selecting a site shows requests for that exact host alongside PHP output labeled **Shared PHP — all sites**. PHP errors may belong to another site; they are not correlated with the selected site's requests. In this scope, Source offers Requests and Shared PHP. Other service logs remain under All sites. Service shortcuts clear the site scope. Legacy access entries without recorded hosts stay global. This uses existing request metadata; it introduces no per-site log files or Nginx/PHP logging configuration.
- Source filters cover All sources, PHP, Web server, Requests, MySQL, and Mail. Search matches displayed messages and source names. Filters survive navigation during the current app session.
- Live updates run approximately every 1.5 seconds while the page and document are visible. Pause freezes the displayed snapshot; Refresh reads once while paused, and Resume follows output again. Copy shown copies exactly the filtered entries as text.
- Recent entries show source and severity, preserve multiline PHP traces, and render as plain text. Known timestamps are ordered chronologically; undated output follows in source order. Scrolling back preserves the visible entry while it remains within the bounded history. New output follows automatically when the reader is at the bottom.
- Empty history, no matching problems, unavailable sources and read failures are distinct states. Current service failures also appear, including failures before a service can open a log.

## Sources and limits

The viewer reads only fixed Fairway-owned log filenames. PHP, PHP-FPM/process, Nginx/process, MySQL/process, Mail process and HTTP access logs are included. PHP logs remain **shared across sites**; the viewer does not guess site attribution from file paths. Request messages include requested host, HTTP/HTTPS, port, original path, status and duration. Query strings, request bodies, cookies and authorization headers are not included in the new request format. Original service error logs can still contain paths or request details; Copy is an explicit action and logs remain excluded from diagnostic reports.

Each snapshot reads at most the latest 64 KiB and displays at most 120 entries per file (nine files). Each displayed message is limited to 4 KiB; the UI renders at most 240 matching entries, prioritizing errors and warnings before recent unclassified/activity output, and explains when narrowing filters is needed. Existing combined-format access logs decode valid escaped UTF-8; TLS handshakes on HTTP ports show a protocol-mismatch explanation. URL display decodes non-ASCII UTF-8 sequences while preserving escaped ASCII separators. Only one native read is admitted at a time. Unchanged snapshots retain existing rows. Special files are rejected without waiting on pipes. Reads run outside the service-manager lock, and are bounded even when a service writes continuously. Complete lines are reread from a fresh handle, so partial writes wait until complete and truncated/replaced files do not produce stale appended duplicates. This is recent troubleshooting history, not a durable event archive or precise cross-service request tracing.

Before starting an owning service, files over 2 MiB are trimmed to their latest 256 KiB at a line boundary. Other services' files are untouched. Running logs are never truncated or renamed: long-running sessions may exceed that threshold until the next start. This avoids races with native open log handles; continuous disk rotation remains separate work.

Framework application logs, arbitrary files, terminal transcripts, SQL queries, external telemetry and per-site PHP configuration are outside this feature. Linux CLI/TUI log access remains unchanged; shared generated access-log formatting and stopped-service retention apply there too.

## Verification before candidate freeze

Unit tests cover bounded reads, partial writes, multiline errors, severity/status classification, replacements, unreadable files, and stopped-service retention. Browser checks cover site/source/search filters, exact host isolation with shared PHP, default problem focus, safe text, copy scope and recoverable clipboard failures, pause/refresh/resume, overlapping navigation reads, honest empty/unreadable states, failure retention during a burst, polling lifetime and minimum-window layout. Copy failures use the fixed notice and do not move the log view; unreadable files stay on the page. The native browser test uses bundled Nginx/PHP with isolated user data. Windows and Mac installer workflows include that native test. Exact candidate installers still require device acceptance, including native window visibility, HTTP/HTTPS and restarting services.
