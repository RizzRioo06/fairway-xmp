# Signed releases and updater channels

Beta 3 is the manual bootstrap for automatic desktop updates. Beta 2 and earlier do not contain a feed or verification key, so students install beta 3 once by hand. Linux continues to update manually. Windows Authenticode signing is deferred; the updater's minisign signatures are enabled independently.

## Credentials

`packaging/updater.pub` is the public verification key. Keep its private key outside the repository, with an offline backup. The existing GitHub secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` sign version-bound update artifacts. Release builds fail if signing inputs are absent or do not match.

The Mac release runner imports only the release identities supplied in `APPLE_CERTIFICATES_P12` (base64 PKCS#12) using `APPLE_CERTIFICATES_PASSWORD`. The current identities are `Developer ID Application: Ei Maung (4Q27NQ2UAF)` and `Developer ID Installer: Ei Maung (4Q27NQ2UAF)`. `APPLE_API_PRIVATE_KEY`, `APPLE_API_KEY`, and `APPLE_API_ISSUER` provide notarization credentials. An ephemeral keychain stores the profile; failed imports clean up partial credentials, and unconditional cleanup removes the keychain immediately after signing/notarization, before bundled code is executed. Its inactivity timeout is one hour. Local builders can instead use the validated `fairway-notary` Keychain profile. Never put private keys or exported identities in the repository or build artifacts.

## Signing and build separation

Desktop workflows compile/test dependencies, prepare runtimes and build helpers/probes on runners without signing secrets. They transfer unsigned apps/installers and lifecycle inputs within the same workflow run to fresh packaging runners. The Mac transfer uses tar to preserve app permissions and symlinks; Windows retains the exact installer bytes. Transfer artifacts expire after one day and contain no credentials. A retry after they expire needs a fresh build.

Packaging runners install the npm lockfile with lifecycle scripts disabled and do not restore Rust/build caches or invoke application/dependency compilation. Tauri CLI 2.12.2 and its platform binaries are locked in `package-lock.json`. Updater-enabled builds use the existing release overlay and the locked CLI's `--no-sign` option, preserving the application's updater configuration, public key, signed-version requirement and update endpoint. Final updater signatures are created directly with the installed CLI and the application version.

Signing is limited to commits already in fetched `origin/main` history, including historical comparison commits and tags at those commits. The standalone source ref is validated from the dispatch checkout before checking out comparison code. Packaging checks out and revalidates the exact build commit. Comparison sources must include the locked-tooling/signing workflow support. Unsigned installer builds remain available on other branches. These repository checks prevent accidental signing of unmerged inputs; protecting main and restricting who can edit/dispatch credential-bearing workflows remain repository administration responsibilities.

Mac packaging uses `FAIRWAY_DEFER_RUNTIME_CHECKS=1` and `FAIRWAY_DEFER_UPDATER_SIGNATURE=1` while Apple credentials are present. It signs/notarizes/staples using system tools without executing the bundled app or PHP. The temporary Apple keychain is then removed. A separate step supplies the updater key only to the signer, and all PHP JIT/Composer, native helper/payload, installed-app and updater checks execute afterward. Local packaging retains its usual checks by default.

Only publication jobs have repository write permission. The signature verifier is compiled in a separate read-only job and transferred to publication; hosted publication fails if that prebuilt verifier is absent. Local publication can still compile the verifier normally. Checkout credentials are not persisted in the signing or publication workspaces.

## Build and verify

Dispatch **Release candidate** (`release-candidate.yml`) from the reviewed commit, or push a `candidate-*` tag at that commit. Candidate tags trigger builds only; they do not publish releases or promote the feed. It runs UI review and the reusable Mac, Windows, and Linux jobs. Signed release inputs are explicit; standalone development jobs remain unsigned unless requested.

Mac packaging signs all Mach-O code in the final app, notarizes and staples the app, then creates the `.pkg` and `.app.tar.gz` from that app. The installer is separately signed, notarized, and stapled. Ticket delivery retries transient Apple/CloudKit failures a bounded number of times; local ticket validation and Gatekeeper acceptance remain mandatory. The updater archive is signed with minisign and bound to its release version. Gatekeeper, stapler, and codesign checks must pass. Only PHP interpreters receive Apple’s `allow-jit` entitlement for PCRE JIT; regex JIT and Composer must run on all four signed PHP versions before notarization. The desktop app, Nginx, MySQL, and libraries receive no JIT exception. A notarized pkg alone would not establish that the app inside an updater archive can run.

Windows creates a normal current-user NSIS installer and its version-bound `.sig`. The same setup executable supports first installation and in-app replacement. `updater_probe` uses the real Tauri updater on a disposable hosted runner: it rejects a tampered download and a signed-version mismatch while services stay ready, downloads the exact candidate, backs up databases, gracefully stops services, removes only stopped PID markers, and installs. The normal installed-data probe then verifies the project, database, selected PHP, settings, backups, and CLI. This is an explicit same-version reinstall drill; production keeps normal semver comparison. Human testing of a later version, restart, native UI, and system prompts remains separate.

Review the exact candidate's acceptance template and UI report. Do not mark unperformed human checks complete. Mac and Windows acceptance includes Sites/HTTPS and a subsequent-version update/restart. The candidate records the installed binaries' commit/version and every installer/updater/signature hash. Rebuild after application changes; never reuse an old tag for changed bytes.

The Mac hosted runner installs and upgrades the pkg in `/Applications`, then relocates that exact installed code to a writable directory with per-user ownership for the native updater drill. Ownership changes do not alter signed code; the signature is checked before the test. The updated bundle returns to `/Applications` before checking preservation, removal, and reinstallation. The lifecycle record states this scope explicitly. A protected `/Applications` update, including approving or cancelling the macOS authorization prompt, still requires human acceptance; the automated drill does not approve that case. A stalled Mac probe is sampled before failing after two minutes.

## Publication and feed promotion

Prepare/review release notes and create a version tag at the successful candidate's exact source commit. Dispatch **Publish tested release** (`publish-beta-release.yml`) with its run ID, commit, tag, reviewed notes path and pre-publication acceptance JSON path (mandatory for RC/stable). Only the human in-app update/restart check follows publication and feed promotion; other device checks and signed-updater CI must pass beforehand. Published evidence keeps deferred checks false and records the pending status in `BUILD-INFO.json`. Follow the [two acceptance phases](beta-acceptance.md#acceptance-before-and-after-publication), then record a real subsequent-version update and protected Mac prompt result. A failure stops further rollout. Set promote_updates explicitly when it is time to offer the release in-app. This is an explicit publication action; building a candidate never publishes a release.

The publisher downloads only that candidate, rechecks its file hashes, verifies both updater signatures and authenticated release versions against `packaging/updater.pub`, and creates a draft with the exact files. Betas/RCs are prereleases; stable versions are ordinary releases marked latest. It compares GitHub asset digests/sizes before publishing the numbered release. Feed promotion is off by default and can run only after the versioned release exists.

The existing preview endpoint is `https://github.com/eimg/fairway-xmp/releases/download/beta-feed/latest.json`. The `beta-feed` prerelease holds only this file; it points to the immutable numbered release's Mac archive and Windows installer and carries their signatures. GitHub's `/releases/latest/` endpoint omits prereleases. Feed promotion understands numbered beta → RC → stable ordering and refuses downgrades. Stable builds use `https://github.com/eimg/fairway-xmp/releases/download/stable-feed/latest.json`; stable promotion updates that feed and the legacy preview feed so beta/RC users can move to stable. A newer next-release preview is preserved. After installing stable, users follow the stable-only feed. See [RC preparation](rc-preparation.md). If feed publication fails, the versioned release stays available for manual installation. Each feed retains its previous value until that feed is successfully updated; rerun only `scripts/publish_release_feed.py` with `GH_REPO` and `FAIRWAY_TAG` to retry. Do not overwrite a published installer's bytes.

## Local Mac app

The local profile is `fairway-notary`. An enabled release build needs the release overlay from `scripts/configure_release.py`; plain development builds intentionally have no updater. Use the signing identities above and `APPLE_NOTARY_PROFILE=fairway-notary` with `scripts/package_macos.sh`. `FAIRWAY_SIGNED_RELEASE=1` requires all Apple credentials plus the updater signing key and produces signed updater artifacts. Test the standalone signed app without installing the pkg when desired.
